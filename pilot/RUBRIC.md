# Rubrics and report format — frozen

## Per-task scoring (implemented in score_pilot.py)

### R — Read
Extract the first JSON object from the raw output. **Correct** iff it
deep-equals the item's expected facts (vlan-id keys normalized to
strings; `trunk_allowed` compared as a set). Failure classes:
`unparseable`, `facts_mismatch`.

### P — Predict / Edit
Extract the first JSON object. The object IS the model output in the
engine's own shapes: a plan (`{"device", "operation", ...}` or
`{"device", "steps": [...]}`), a clarify (`{"type": "clarify", ...}`),
or the pilot-surface no-op (`{"type": "no_op"}`). Grade with the
Phase 2 engine (`src/plan/`): `validate_output()` must pass and
`apply_plan()` must apply cleanly. Then:
- plan items: every golden assertion must hold after apply, **and**
  `diff_states()` must show no changed path outside the asserted set
  (preservation is graded). Failure classes: `unparseable`,
  `wrong_kind`, `validation_error`, `assertion_failed`,
  `preservation_violation`.
- no_op items: correct iff the output is `{"type": "no_op"}`, or a
  plan whose apply changes nothing.
- clarify items: correct iff the output is a clarify object whose
  reason matches exactly and whose candidate set matches exactly
  (order-insensitive). Failure class: `clarify_mismatch`.

### E — Explain
**Correct** iff (a) the final `Citation:` line equals the item's
expected citation (module + path, whitespace/case-normalized), and
(b) every expected key point appears in the answer text
(case-insensitive substring). Failure classes: `citation_missing`,
`citation_mismatch`, `keypoint_missing`. This is a strict rubric by
design; raw outputs are kept so a human can re-grade leniently and the
two grades can be reported side by side.

## Report format (results/RESULTS.md, generated by the scorer)

One table, one row per (task, arm) — with P additionally split by view:

| Task | Arm | View | Correct | Items | Accuracy |

Denominators are always shown; no pooled "overall accuracy" headline
number. Below the table: failure-class counts across all incorrect
items. The full per-item records land in `results/scores.json`, and
`results/raw_outputs.jsonl` preserves every raw generation with its
prompt hash, so any number in the report can be traced to the exact
prompt and output that produced it.

Paired-view agreement (both views correct / one / neither) for R and P
is computed from scores.json in the run report posted to the board; it
is the reading-vs-deciding diagnostic: JSON-right/CLI-wrong indicates a
reading problem, both-wrong a decision problem.
